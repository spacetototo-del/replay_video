## 0. 요구사항 정리 (최신, 확정)

### 확정된 요구사항 [stated]
1. 폰/태블릿 화면에는 항상 라이브 카메라 프리뷰가 보여야 함
2. 저장 버퍼는 3분 — 3분이 지난 영상은 계속 자동 삭제
3. 화면을 손가락으로 뒤로 드래그하면 최근 3분 이내를 리와인드해서 다시 볼 수 있어야 함 (다이빙장 아이패드 앱과 동일한 UX)
4. 갤럭시 워치6에 카메라 프리뷰를 띄우고, 워치의 REC 버튼을 누르면 녹화 시작, STOP 버튼을 누르면 녹화 종료 (워치 기본 카메라 컨트롤 앱과 같은 UX)
5. 목표 해상도/화질을 앱 설정에서 조절 가능해야 함
6. 저장공간은 10GB 여유만 있어도 충분한지 확인 필요
7. 평소엔 화면이 디밍되어 있다가, 워치에서 신호가 올 때만 화면이 깨어나는 동작을 원함

### 여전히 확인이 필요한 것
- **목표 해상도/프레임레이트 기본값**: 1080p30을 기본값으로 가정하고 설계함(확인 필요) — 설정에서 바꿀 수 있게 만들 것이므로 초기값만의 문제
- **워치 REC/STOP과 "리와인드 3분 버퍼"의 관계**: 아래 8절에서 설계상 중요한 트레이드오프이므로 반드시 한번 확인 필요
- **워치에 진짜 매끄러운 실시간 영상까지 필요한지, 아니면 "지금 화면이 이런 느낌이다" 정도의 저해상도/저프레임 근사 영상이면 충분한지**: 9절 참고, 완전한 실시간 영상은 난이도가 크게 뜀

## 1. 결론 (아키텍처 요약)

여전히 **세그먼트 기반 롤링 버퍼**가 골격입니다. 다만 이번 요구사항 때문에 두 가지가 추가됩니다.

1. **폰 쪽 재생 엔진**: 저장용 물리적 병합(Media3 Transformer)과는 별개로, 화면에서 "3분 리와인드 스크럽"을 보여주려면 **Media3 ExoPlayer의 재생목록(Playlist) 기능**으로 세그먼트 파일들을 순서대로 이어서 하나의 연속된 타임라인처럼 재생/탐색(seek)할 수 있게 구현합니다. 이건 실제로 파일을 합치는 게 아니라 "이어서 재생"하는 것이라 훨씬 가볍고 빠릅니다. 실제 병합은 "저장" 버튼을 눌렀을 때만 일어납니다.
2. **워치 연동 방식 재설계**: 단순 "신호 1개 → 과거 2분 저장"에서 "REC/STOP 2버튼"으로 바뀌면서, 실제로 워치가 폰의 카메라를 직접 시작/정지시키는 방식 대신 **"항상 돌아가는 버퍼에 시작/종료 마커(marker)를 찍는 방식"**을 권장합니다 — 이유는 8절 참고.

## 2. 전체 아키텍처 (개정)

```
[갤럭시 워치6 - Wear OS 앱]
   REC 버튼 탭 → "/mark_start" 전송
   STOP 버튼 탭 → "/mark_end" 전송
      │  MessageClient.sendMessage(...)
      ▼
[폰 - WearableListenerService]
      │  onMessageReceived()
      ▼
[폰 - RecordingService (Foreground Service, 항상 실행 중)]
   ├─ CameraX Recorder: 계속 15~20초 세그먼트 녹화, 3분 초과분 자동 삭제
   ├─ SegmentRotationManager: 버퍼 유지시간(3분) 관리
   ├─ MarkerManager: 워치에서 온 시작/종료 시각 기록
   ├─ ClipExporter: 종료 마커 수신 시 [시작,종료] 구간을 Media3 Transformer로
   │                 물리적 병합 + 트림 → MediaStore(갤러리)에 저장
   └─ 워치에 "저장 완료" 응답 전송 (진동 피드백)

[폰/태블릿 UI - 항상 화면에 표시]
   ├─ 라이브 프리뷰(PreviewView) — 지금 카메라가 보는 화면
   └─ 리와인드 모드 진입 시 → ExoPlayer Playlist로 최근 3분 스크럽 재생
```

## 4. 단계별 구현 계획 (개정된 마일스톤)

### Phase 0 — 프로젝트 셋업 (0.5일)
v1과 동일. CameraX, Media3(Transformer + ExoPlayer 둘 다 필요해짐), Wearable 라이브러리 추가.

### Phase 1 — 카메라 세그먼트 롤링 버퍼 (2~3일)
v1과 동일하되 **버퍼 유지시간을 3분(+ 안전마진 30초~1분)**으로 설정. 세그먼트 길이는 15~20초 권장(스크럽 정밀도와 관리 부담의 균형).

### Phase 2 — 상시 라이브 프리뷰 + 리와인드 스크럽 (신규, 2~3일 — 이번 요구사항 중 난이도가 가장 높은 부분)
- `PreviewView`로 상시 라이브 프리뷰 표시 (기본 화면)
- 화면을 아래로 스와이프하거나 하단 핸들을 드래그하면 "리와인드 모드" 진입
- 리와인드 모드: ExoPlayer에 최근 3분 치 세그먼트 파일들을 순서대로 `MediaItem` 리스트로 등록 → 사용자가 타임라인 바를 드래그하면 해당 위치가 몇 번째 세그먼트의 몇 초 지점인지 계산해서 `player.seekTo(mediaItemIndex, positionMs)` 호출
- 리와인드 모드에서 원하는 장면을 찾으면 "이 지점부터 저장" 같은 수동 저장 버튼도 함께 제공 (워치 없이도 쓸 수 있게)
- 라이브 프리뷰로 복귀하는 버튼/제스처

### Phase 3 — 저장(Export) 로직 (1~2일)
- v1과 동일하되 트리거가 "마커 2개(시작/종료) 사이 구간"으로 바뀜
- 종료 마커가 시작 마커보다 3분(버퍼 유지시간)보다 더 오래 지난 경우: 이미 지워진 앞부분은 저장 불가 → 사용자에게 "일부만 저장됨" 안내 필요

### Phase 4 — 워치 앱: REC/STOP UI (1~1.5일)
- Compose for Wear, 네이티브 카메라 앱과 유사한 REC(빨간 원)/STOP(정사각형) 버튼
- REC 탭 → `/mark_start` 전송 + 워치에 녹화 중 타이머 표시(00:00부터 증가)
- STOP 탭 → `/mark_end` 전송 + "저장 중..." → 폰 응답 오면 "저장됨" 표시
- 폰과 연결 안 되어 있을 때 상태 표시

### Phase 5 — 워치 라이브 프리뷰 (신규, 선택 기능 — 9절 검토 후 진행 여부 결정)
9절에서 다루는 기술적 제약 검토 후, 필요하면 저프레임 스냅샷 스트리밍 방식으로 구현 (별도 Phase로 분리해서 MVP 이후 진행 권장)

### Phase 6 — 설정 화면: 해상도/비트레이트 (0.5~1일)
- CameraX `Recorder`의 `Quality` 옵션(SD/HD/FHD/UHD) 및 커스텀 비트레이트 노출
- 설정 변경 시 진행 중이던 버퍼는 초기화(해상도가 바뀌면 기존 세그먼트와 이어붙이기 불가하므로)

### Phase 7 — 워치-폰 연동 (0.5~1일)
v1과 동일 (Data Layer API, 페어링/서명 이슈 등)

### Phase 8 — 화면 절전/깨우기 (신규, 0.5~1일) — 11절 참고

### Phase 9 — 안정성/배터리 (지속)
v1과 동일 + 저장된 클립(내보낸 완성본)이 계속 쌓이는 문제에 대한 정리 정책 추가 (10절 참고)

### Phase 10 — 실사용 테스트 (0.5~1일)
- 라이브 프리뷰 → 리와인드 스크럽 → 워치 REC/STOP → 저장까지 전체 시나리오 리허설

## 5. 예상 총 작업 기간 (개정)

리와인드 스크럽 UI와 워치 REC/STOP 연동이 추가되면서 v1 대비 작업량이 늘었습니다. 실작업 기준 **10~14일 정도(주말/퇴근 후 작업 기준 4~5주)**로 추정합니다. 워치 라이브 프리뷰(9절)를 MVP에 포함시키면 여기서 추가로 3~5일 더 걸릴 걸로 봅니다. 이 추정치는 의견이며, 실제로는 Phase 2(리와인드 스크럽)와 Phase 5(워치 프리뷰, 진행 시)에서 가장 시간이 걸릴 가능성이 높습니다.

## 8. 설계 재검토 — 워치 REC/STOP을 "실제 녹화 시작/정지"가 아니라 "마커 찍기"로 구현하길 권장하는 이유

사용자 요청은 "워치 기본 카메라 컨트롤 앱처럼 REC 누르면 녹화 시작, STOP 누르면 정지"입니다. 이걸 문자 그대로 구현하면, **워치에서 REC를 누르는 순간부터 촬영이 시작**되는 것처럼 동작합니다. 그런데 이 방식은 애초에 이 앱을 만드는 이유(상시 버퍼로 "이미 지나간 순간"도 건질 수 있게 하는 것)와 충돌합니다 — 다이빙을 시작한 다음에야 워치를 누르면, 누르기 전 도약 장면을 놓치게 됩니다.

그래서 다음과 같이 권장합니다 (이건 제 판단이며, 사용자가 원하는 그대로의 UX와는 다를 수 있어 확인이 필요합니다).

- 카메라는 **항상 세그먼트 버퍼로 계속 녹화 중** (v1과 동일, 절대 멈추지 않음)
- 워치의 REC 버튼 = "지금 시점을 시작 마커로 기록"
- 워치의 STOP 버튼 = "지금 시점을 종료 마커로 기록 → 두 마커 사이 구간을 버퍼에서 잘라 저장"
- 사용자가 보는 워치 화면/조작감은 "녹화 시작/정지"와 완전히 동일하지만, 실제로는 이미 계속 녹화되고 있던 버퍼에서 구간을 골라내는 것뿐이라 **REC를 조금 늦게 눌러도 직전 몇 초는 버퍼에 남아있어서 여전히 건질 수 있는 여지가 있습니다** (예: REC를 누른 시점 대신 "REC 누르기 5초 전"부터 시작 마커를 잡는 옵션도 나중에 추가 가능)

이 방식이 아니라 정말로 "워치가 카메라를 물리적으로 시작/정지시키는" 방식을 원하시면 말씀해주시면 그쪽으로 설계를 바꾸겠습니다 — 다만 그 경우 상시 프리뷰/리와인드 기능과는 별개의 녹화 세션을 관리해야 해서 구조가 더 복잡해집니다.

## 9. 워치에 실시간 카메라 프리뷰를 띄우는 것의 기술적 난이도

**사실 확인**: Wear OS용 "카메라 리모컨" 앱들(예: Camera Remote for Wear OS류)이 실제로 존재하고, 워치에서 폰 카메라의 뷰파인더를 보면서 셔터를 누르는 기능을 제공합니다. 삼성 자체 카메라 앱도 갤럭시 워치와 연동해 뷰파인더를 보여주는 기능이 있습니다. 즉 **아예 불가능한 기능은 아닙니다.**

다만 이런 앱들 대부분은 진짜 매끄러운 30fps 영상을 스트리밍하는 게 아니라, **초당 1~수 프레임 정도의 정지 이미지(스냅샷)를 계속 갱신해서 보내는 방식**으로 "실시간처럼 보이게" 만드는 경우가 많습니다(이 구현 디테일은 앱마다 달라서 확인 필요이지만, Bluetooth 대역폭과 워치 배터리 제약을 감안하면 이 방식이 일반적입니다). 진짜 부드러운 실시간 영상 스트리밍은 개인 프로젝트로는 난이도가 급격히 올라갑니다.

**권장 접근 (2단계)**:
1. **1단계(MVP)**: 워치에는 REC/STOP 버튼과 텍스트 상태(녹화중 00:12, 저장됨 등)만 표시. 실제 화면 확인은 폰/태블릿에서.
2. **2단계(추후, 선택)**: 폰에서 카메라 프레임을 1~2초 간격으로 저해상도 JPEG로 캡처해서 워치로 전송(Wearable `Channel API` 또는 `Asset` 활용), 워치 화면에 이미지로 갱신 표시. 진짜 영상은 아니지만 "지금 카메라가 이 각도를 보고 있다" 확인 용도로는 충분.

**리스크/반론**: 2단계까지 하려면 개발 기간이 꽤 늘어납니다(5절 참고). 처음부터 다 만들려고 하지 말고 1단계로 실사용해보면서 "워치 화면에 프리뷰가 정말 필요한지" 재평가하는 걸 권장합니다.

## 10. 저장공간 10GB로 충분한지 (계산)

버퍼는 3분(+여유 약 1분 = 4분)만 유지하고 자동 삭제되므로, 상시 필요한 버퍼 공간은 해상도별로 다음과 같이 추정됩니다 (일반적인 H.264 인코딩 비트레이트 기준 추정치이며, 실제 기기/인코더에 따라 달라질 수 있어 확인 필요).

| 해상도/프레임 | 예상 비트레이트 | 4분 버퍼 예상 용량 |
|---|---|---|
| 720p30 | 약 4 Mbps | 약 120 MB |
| 1080p30 (기본값 가정) | 약 8 Mbps | 약 240 MB |
| 1080p60 | 약 12 Mbps | 약 360 MB |
| 4K30 (확인 필요) | 약 35 Mbps | 약 1,050 MB (~1GB) |

**결론: 1080p 기준이면 10GB는 버퍼 용도로만 보면 40배 가까이 여유가 있어 충분합니다.** 다만 두 가지를 감안해야 합니다.

1. 저장(export) 처리 중에는 버퍼 + 완성본이 잠깐 동시에 존재하므로 순간적으로 버퍼 용량의 약 2배가 필요할 수 있음 — 그래도 위 표 기준으로는 여전히 10GB에 크게 못 미침
2. **저장된(export 완료된) 클립들은 버퍼처럼 자동 삭제되지 않고 계속 쌓입니다.** 한 세션에 클립을 여러 번 저장하면 이 부분이 누적되어 언젠가 10GB를 넘길 수 있으므로, 별도로 "오래된 저장 클립 수동/자동 정리" 정책이 필요합니다(예: 저장 30일 경과 시 알림, 또는 개수 제한).

## 11. 화면 디밍 → 워치 신호 시 깨어나는 동작 (설계)

**요청 이해**: 평소엔 화면을 어둡게(또는 꺼진 상태) 유지해서 배터리를 아끼고, 워치에서 REC를 누르는 순간 폰/태블릿 화면이 켜져서 상황을 볼 수 있게 하고 싶다는 것으로 이해했습니다 — 확인 필요합니다(맞다면 진행, 아니라면 정정 부탁드립니다).

**구현 방향**:
- 평소: 시스템 화면 자동 꺼짐 시간을 앱이 짧게 유지하도록 두거나(배터리 우선), 혹은 화면은 켜두되 밝기만 최소로 낮추는(디밍) 방식 중 선택 가능 — 완전히 꺼도 `RecordingService`가 Foreground Service라 녹화 자체는 끊기지 않음
- 워치에서 `/mark_start` 신호 수신 시: 폰 쪽에서 화면을 깨우는 처리 필요 — Activity에 `FLAG_TURN_SCREEN_ON` + `FLAG_SHOW_WHEN_LOCKED` 같은 플래그를 걸어 잠금화면 위에서도 즉시 라이브 프리뷰가 뜨도록 처리 (알람 앱들이 쓰는 방식과 동일한 패턴)
- STOP 신호 수신 후 일정 시간(예: 10~15초) 지나면 다시 디밍/화면 꺼짐으로 복귀

**트레이드오프**: 화면을 완전히 꺼두면 배터리는 가장 아낄 수 있지만, 화면이 꺼진 상태→깨어나는 데 약간의 지연(수백 ms~1초 내외로 예상, 확인 필요)이 있을 수 있습니다. 반대로 디밍(꺼짐이 아니라 밝기만 낮춤)으로 유지하면 반응은 즉각적이지만 배터리 소모가 더 큽니다. 처음엔 "디밍" 방식으로 시작해서 실사용 배터리 소모를 보고 "완전히 끄기"로 바꿀지 결정하는 걸 권장합니다.

## 12. 리스크 및 반론 (v1 + 추가)

- (v1 유지) 배터리/발열, 저장공간 관리 버그, 워치-폰 통신 지연/유실, 공용장소 촬영 문제, 기존 상용 앱과의 유사성, 이 계획서는 실제 빌드 검증을 거치지 않은 설계 문서라는 점
- **(신규) 워치 REC/STOP을 마커 방식으로 바꾸는 게 사용자가 원한 그대로의 설계가 아닐 수 있음** — 8절에서 대안을 제시했으나 최종 결정은 사용자 확인 필요
- **(신규) 워치 라이브 프리뷰는 범위를 넉넉히 잡아야 함** — 처음부터 풀스코프로 잡으면 일정이 크게 늘어날 위험, MVP는 REC/STOP+텍스트 상태만으로 시작하는 걸 권장
- **(신규) 리와인드 스크럽 UI(ExoPlayer 플레이리스트 seek)의 실제 체감 반응속도**는 세그먼트 개수/길이 설정에 따라 달라짐 — 세그먼트를 너무 짧게(예: 5초 이하) 잡으면 파일 개수가 많아져 관리 오버헤드 증가, 너무 길게(예: 1분) 잡으면 리와인드 진입 지점의 정밀도가 떨어짐. 15~20초를 시작값으로 제안하지만 실사용하며 조정 필요
